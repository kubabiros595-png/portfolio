How I work with AI

I am not a developer. I build these projects with Claude: I define the problem, the rules and thresholds, what the AI may and may not do, and the expected answer for every test case. Then I run the tests, read the failures and decide on the fixes.

Rules decide before the AI is called

Whether something is a problem is decided by code with fixed thresholds, so the same data always gives the same result and every decision can be explained.

  • Churn Risk Alert: Accounts are scored with fixed rules and a saved reason for every point; the AI never decides who gets an alert.
  • Pharma Implementation Case: Keyword rules flag possible adverse events independently of Claude. Either signal is enough, and the AI can add a safety flag but never remove one.
  • Clinical Trials Monitor: A rule filter decides what is in scope before any summary is written, so no tokens are spent on records that would be rejected.

Code checks what the AI wrote

The AI writes words. Code then checks them against the facts before a person sees anything.

  • Knowledge Assistant: Every cited section must be one the search actually retrieved; one unknown source and the whole answer becomes “I don't know”.
  • Integration Health Monitor: Every number in a draft must come from the facts, and a draft containing a secret or key-like string is removed before saving.
  • Pharma Implementation Case: The AI only returns the ID of an approved response; the draft is assembled in code, word for word, with its source and version.

A person approves

Nothing goes to a customer automatically. Drafts and alerts are saved as pending review, and approval means “ready to copy”.

  • Onboarding Tracker: A review form shows waiting drafts with the result of the code checks; a draft that failed the checks can be approved only with a note.
  • Churn Risk Alert: A login-protected form lets a person set approved, edit or rejected with a note.
  • Site Integration Monitor: Client emails never mention monitoring or competitors, and a person approves every draft.

Tests with deliberately planted errors

A check that never fails proves nothing, so I plant known mistakes and make sure they are caught. I set expected answers before running the tests.

  • Clinical Trials Monitor: Four “canaries”: real AI summaries with a wrong link, phase, status or a dosing instruction planted in them. All four were flagged.
  • Onboarding Tracker: Seven hand-written bad drafts, including one that calls a launch late when it is not. All seven were caught.
  • Knowledge Assistant: A fake AI reply citing a section the search had not found was replaced with “I don't know” and logged.

Reading the output, because checks are not enough

Several times every automated check passed and the output was still wrong. Those cases are documented, not hidden.

  • Onboarding Tracker: In the first draft run every draft passed the code checks, but three were misleading when I read them. The fix changed both the brief and the checks.
  • Site Integration Monitor: Drafts passed the checks but thanked the client “for reaching out” about a problem they never reported. Reading them led to two new checks.
