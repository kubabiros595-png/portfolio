Integration Health Monitor

Catching silent webhook failures

Built and tested on fictional data, not deployed. Three invented online shops, made-up events and secrets.

  • n8n

45 of 45 signed test requests handled as expected; 18 of 18 detector scenarios with 0 false alarms and 0 missed alerts.

My role. I built this project with AI assistance. I defined the scenario, the signature and timestamp rules, the idempotency key, the silence and error-spike rules, what the client should check for each problem, and the draft checks. I set the expected answer for every test case, reviewed the failures and chose the fixes.

Problem

A SaaS company receives webhooks from its clients' online shops. A shop changes a plugin, rotates a signing secret or moves to a new domain, and events simply stop arriving. Nothing errors on the receiving side, because nothing reaches it. The client finds out days later, from their own numbers.

This project receives the webhooks safely, checks every hour whether an integration has gone quiet or started failing, and prepares a short message for the client that waits for a person to approve it.

How it works

  1. InputShop sends a webhook signed with HMAC-SHA256 and a timestamp
  2. Rule (code)Body larger than 64 KB?
    • yes → 413, before any signature work
  3. Rule (code)Signature over the raw body, timestamp within 5 minutes
    • no → 401 + log entry
  4. Rule (code)Required fields and types valid?
    • no → 400 + log entry listing every problem
  5. Rule (code)Same shop + event_id seen before?
    • yes → 200 duplicate, logged only
  6. StoredSave the event; a check after saving keeps only the first copy of parallel requests
  7. Rule (code)Every hour: silent for its own rhythm? Error rate above the limit?
  8. Rule (code)Code picks the facts and what the client should check
  9. AI (Claude)Claude writes the wording of the message only
  10. Rule (code)Code checks the draft: numbers, secrets, other clients, no promised fix, call or free work
    • secret found → draft removed, nothing quoted
  11. PersonAlert saved as pending review; a person approves

Runs in your browser on data copied from the CSV and test files in the repository. No API calls, no keys, no server.

What did not pass the first time, and what I changed

Duplicates arrived before the original (V03/D04, D01/D02).

The test sent requests in parallel, so a repeat sometimes arrived first. The intake behaved correctly for the order it received; I changed the test to send one request at a time. It also exposed a real limit: two identical requests at the same moment could both pass the duplicate lookup. I added a check after saving (the first stored copy wins) and test D06, which sends the same request three times at once.

Broken JSON got 401 instead of 400 (F11).

The n8n HTTP Request node re-encoded a non-JSON body sent as application/json, so the bytes that arrived were not the bytes that were signed. The intake was right to reject it; the test now sends that body as text/plain.

Timestamps aged while waiting.

All requests were signed at the start, and some waited about 10 seconds (one arrived 320 s old instead of 310 s). Each request is now signed just before it is sent.

Secret digits in the check notes (C05).

The check blocked a draft containing the real signing secret, but its note listed digits taken from that secret. Now the note lists no numbers when a secret is found, the draft is removed before saving, and the test fails if any part of the secret appears in the notes.

First monitor results not saved.

The results table was missing two columns. I added them; the first run's results were taken from that execution's output.

Limitations

  • Duplicates are resolved after saving, not prevented by the database. A real deployment would use a unique constraint, which n8n Data Tables do not support.
  • One secret per shop, no rotation window.
  • The silence rule has no time-of-day pattern, and the thresholds were not tuned on real traffic.
  • The daily report has no automated tests; it was checked on one demo run.
  • Draft quality was reviewed by hand on 2 live drafts.
