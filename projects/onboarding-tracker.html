Problem

In B2B SaaS, the time between “contract signed” and “client sees value” is where many accounts are won or lost. Implementations stall quietly: the client has not sent API keys, a stage has had no update for a week, or the launch date promised in sales can no longer be met.

Spreadsheets show what is planned, not what is late. This workflow builds the plan from a template when a contract is signed, checks every project each working day, flags the ones that are slipping and drafts client emails that a person reviews.

How it works

  • Input or storage
  1. InputContract signed form: plan, technical contact, integrations, target launch
  2. Rule (code)Plan from a template: 8 stages with owners and business-day deadlines
    • plan ends after the target → warning on day one
  3. InputStage update form
    • closing a stage while an earlier one is open, a block without a note or a future date → refused
  4. Rule (code)Every weekday: overdue, stalled, blocked, launch at risk → green, yellow or red
    • same reminder sent recently → held
  5. Rule (code)Weekly brief built from the table and the daily check
  6. AI (Claude)Claude writes the wording of kickoff and weekly status emails only
  7. Rule (code)Code checks every date, stage and promise
  8. PersonReview form: approve, send back for edits or reject, with a note

What did not pass the first time, and what I changed

Rules test, first run: 35 of 39.

Four stage-update checkpoints came back as “no result”. The bug was in the test, not in the rules: the scoring node read only the first of five results. Switched off that setting, re-ran: 39 of 39.

Drafts, run 1: all passed the code checks, but 3 were misleading when I read them.

One said “Everything is on schedule” for a project whose launch was at risk; one repeated an old target date; one asked for a file by a date that had already passed. Every date came from the plan, so the date check passed, but the dates were out of date. The brief now uses the daily-check state, and the code check flags past deadlines, “on track” when health is not green and a missing realistic launch date.

Drafts, run 2: a false alarm in my own check.

A kickoff email said “we cannot promise that earlier date”, which is the honest wording, and the check reacted to the word “promise”. The check now ignores a denied promise.

Drafts, run 4: a repeat with no changes found a new mistake.

One status called the launch late when the projected date was before the target. I added a check, a prompt rule and a planted bad draft for this case. The trial account hit its execution limit, so the fix was tested on the saved drafts, not on fresh ones.

Limitations

  • Fictional data and thresholds I chose; not tuned on real implementations.
  • No public holidays in the business-day calendar.
  • Reminders are logged, not sent. Drafts are never sent.
  • The code checks catch specific risky patterns; they do not judge whether an email makes sense. Run 1 showed why a person still reads every draft.
  • The review form page itself was not clicked through by a person.
