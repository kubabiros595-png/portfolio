Case study

Automation Ideas Tracker

Ranking automation ideas by hours saved per day of effort

Built and tested on fictional data, not deployed for a real team. Ten fictional sample ideas. This one has no AI step. A demo with sample data runs on GitHub Pages.

  • SQLite in the browser
  • SQL
  • Automated tests
  • No AI

25 of 25 automated tests pass (11 formula, 14 SQL), run by GitHub Actions on every push.

My role. I built this project with AI assistance. I defined the problem, the form fields, the formula, the effort per complexity, the approval rule and the statuses, chose the sample ideas from Customer Success work, set the expected test results and checked the app on desktop and phone.

ProblemHow it worksTest resultsWhat I fixedLimitationsRepository

Problem

Customer Success and Support teams collect many ideas for automation, but usually the loudest one gets built first. Nobody compares how much time each idea would save against how hard it is to build.

Ideas that touch customer data also need approval from a data owner, and that step is easy to forget. This is a small static web app with a SQLite database inside the browser: no server, no API keys and no AI.

How it works

  • Rule in code
  • AI step
  • Person decides
  • Input or storage
  1. InputTeam member submits a manual process they repeat every week
  2. Rule (code)Formula: hours saved per month, effort in days, priority = hours ÷ effort; personal data → needs approval
  3. StoredINSERT with named parameters into SQLite in the browser
  4. Rule (code)Priority list and summary from SQL (WHERE, ORDER BY, GROUP BY)
  5. PersonA person changes the status; every change goes to the history

The tests show that the formula and the queries behave as designed. The time estimates are only as good as the numbers people enter.

What did not pass the first time, and what I changed

Hidden tab on phones.

On a 375 px screen the fourth tab was cut off. I made the tabs smaller on narrow screens.

The test command did not find the tests.

It failed on a newer Node version; the command now uses an explicit file pattern.

Broken dependency file.

A command meant to pin the library version created a wrong entry and npm stopped working. I fixed the file and pinned the exact version stored in the repo.

Wrong test expectation.

My first SQL test expected 24 history rows, but the sample data has 21. The test caught my own counting mistake.

Limitations

  • Data is stored only in the user's browser; a real team would need a shared database and logins.
  • Clearing browser data deletes the ideas. There is no export yet.
  • The formula ignores building cost in money, maintenance time and risk.
  • The approval flag is a reminder; it does not stop anyone from changing the status.
