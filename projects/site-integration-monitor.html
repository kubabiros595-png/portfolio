Site Integration Monitor

Early technical churn signals from public website code

Built and tested on fictional data, not deployed. Ten invented shops served by a test webhook; the vendor and its script are fictional.

Problem

A SaaS product that installs on the client's website with a script can lose a client quietly. The client's team adds a competitor's script, or removes ours during a redesign, and nobody says anything. Usually it shows up only when results drop or the cancellation arrives, and by then the conversation is about leaving, not about fixing.

Once a day this workflow reads the public code of each client's homepage and checks whether the (fictional) script is still installed and whether a competitor's script has appeared.

How it works

  • Rule in code
  • AI step
  • Person decides
  • Input or storage
  1. InputDaily: fetch each client homepage (public pages only)
    • 403 → “cannot check”, no workaround
    • 5xx → skip the day, keep the state
  2. Rule (code)Read only script tags the browser would run (comments, text and JSON-LD ignored)
  3. Rule (code)Look inside the Google Tag Manager container and service worker files
  4. Rule (code)Match against a signature table built from vendors' public docs
  5. Rule (code)Same change on 2 scans in a row?
    • no → pending, wait for the next scan
  6. Rule (code)Alert level: urgent if our script is gone, high if a competitor appeared
  7. AI (Claude)Claude drafts an internal alert and a client email (the email prompt never sees vendor or client names)
  8. Rule (code)Code checks the drafts
  9. PersonPending review by a person; nothing is sent

What did not pass the first time, and what I changed

The test loop stopped after day 1, twice.

The scanner's last node was a filter with nothing to pass on, so the test loop never continued. The scanner itself was right. I added a final node that always returns a summary row; the third run passed.

Code checks passed, my own reading did not.

Two technical-help emails thanked the client “for reaching out” and apologised, as if the client had reported a problem. They had not. I added a prompt rule, two code checks and two hand-written test emails.

Then the subjects.

The bodies were now careful, but two subjects still stated the problem as a fact. I added a subject check, a prompt rule and one more test email. The next run passed and I found nothing wrong reading it.

Last change, not fully re-tested.

After the draft tests I added scenarios I and J and a “not found” evidence line. The detection test passed with these changes, but the trial hit its execution limit, so the draft test was not run again.

Limitations

  • Public code only: no login, no forms, no private pages; once a day; a block stops the check.
  • Scripts that load only after cookie consent, or are injected at runtime, are invisible to this method.
  • Vendor signatures go stale and need an owner.
  • Client emails never mention monitoring or competitors. Not legal advice: a real deployment needs a check against the client contract and local law.
