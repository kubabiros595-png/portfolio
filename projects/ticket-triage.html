Case study

Ticket Triage

AI-assisted support triage with confirmed-only answers

Built and tested on fictional data, not deployed. Invented tickets in English, Polish and Spanish for an invented product.

  • n8n
  • Support
  • Masking
  • Claude

On 30 unseen tickets: 30 of 30 categories correct and 0 wrongly marked as not needing a person.

My role. I built this project with AI assistance. I defined the workflow rules, used synthetic data, required human review and confirmed-only answers, reviewed the test results and chose the improvements.

Problem

Support teams spend time reading every ticket, judging its urgency and searching for the right answer. Serious problems can look minor.

A confident AI reply can be wrong if it is not tied to confirmed product knowledge, so the model may only use a fictional “product bible” and must report gaps.

How it works

  • Rule in code
  • AI step
  • Person decides
  • Input or storage
  1. InputRead tickets; skip those a person has already handled
  2. Rule (code)Mask personal data before anything goes to the model
  3. AI (Claude)Claude assigns category, urgency and a short reason
    • AI call fails after retries → ticket goes to a person
  4. Rule (code)Code checks that the result uses allowed values
  5. AI (Claude)Claude drafts a reply from the product bible and lists the entries it used
  6. Rule (code)Code checks sources, panel paths, length, risky promises, internal labels, placeholders
  7. PersonSaved as pending review with knowledge gaps and warnings

Test results

I set the expected answers before the unseen test ran, and I did not change the rules during that test. The set included angry messages, urgent outages, personal data, security issues, unclear messages and prompt injection attempts.

What did not pass the first time, and what I changed

Masking mistakes.

Dates looked like phone numbers, names with accents were missed, and a customer called Theo caused the word “the” to be masked. Each case became a test.

Weak draft steps.

Some drafts repeated steps the customer had already tried. A new rule requires steps to fit the problem.

Too broad security rule.

A simple password reset request was treated as a security incident. I narrowed the rule.

Cut-off JSON and a false alarm.

The model used part of its token limit for reasoning, so JSON answers were cut off; I raised the limits and kept the JSON check. A draft check removed “Home” from a panel path; I changed the order of the checks.

Limitations

  • Rule-based masking misses some names and sometimes masks normal text. Real customer data would need a stronger detection tool, plus legal and security approval.
  • Sending the whole product bible works only for a small knowledge base; a larger one would need retrieval.
  • Code checks catch risky wording, but cannot judge whether every suggestion is sensible.
  • Some remaining issues after the retest are listed openly in the test results (for example a thank-you message with the wrong urgency).
