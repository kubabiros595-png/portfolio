Churn Risk Alert

Daily account alerts with human review

Built and tested on fictional data, not deployed. Invented customer accounts, including edge cases just below and above each threshold.

My role. I built this project with AI assistance. I defined the scoring rules, the deduplication rule, the review process and the email rules, set the expected answers for every test case, reviewed the drafts and chose the improvements.

Problem

Customer Success teams often notice a struggling account too late: usage drops, tickets pile up and nobody has talked to the customer in weeks.

A weekly report does not react on the day a threshold is crossed. A daily alert has the opposite risk: it repeats the same warning every morning until people stop reading it.

How it works

  • Rule in code
  • AI step
  • Person decides
  • Input or storage
  1. InputEvery weekday: read account data
  2. Rule (code)Score each account with fixed rules and save the reason for every point
    • empty value → reported as missing, not as zero
  3. Rule (code)At least 6 points and no open alert from the last 7 days?
    • open alert → skipped, unless the score rose by 2 or more
  4. Rule (code)Code picks one email topic and the one fact the email may mention
  5. AI (Claude)Claude writes the subject and body only, without the account name or metrics
    • AI call failed → saved as NO DRAFT, retried next day
  6. Rule (code)Code checks: no invented numbers, promises, discounts, meeting requests or monitoring language
  7. PersonLogin-protected review form: approved, edit or rejected, with a note

Test results

The evaluation workflow sends test accounts through the same scoring and deduplication code as the daily run, without calling the AI or writing alerts. The cases cover values just below and above every threshold, the 7-day window, score rises of 1 and 2 points, every review status and a failed draft.

What did not pass the first time, and what I changed

Cut-off answers.

The model used part of its token limit for reasoning, so 3 of 4 drafts in the first run were invalid JSON. I raised the limit and kept the JSON check.

Drafts that sounded like monitoring.

Emails quoted usage drops back to the customer and opened with “I wanted to reach out”. Code now picks one topic and one allowed fact, and the email ends with a question the customer can answer in one line.

Internal notes in customer emails.

One draft congratulated a customer on a new hire it only knew from an internal note. Notes no longer go to the model at all.

Failed drafts blocked accounts; an open review form.

An alert without a draft blocked the account for a week; it now gets a new attempt the next day, with its own test case. The review form now requires an n8n login.

Limitations

  • The thresholds are a reasonable starting point, not tuned on real churn data. The tests show the rules behave as designed, not that they predict who will leave.
  • If the data sync failed, the workflow would score yesterday's data; a real deployment needs a freshness check.
  • Email quality was reviewed by hand on 4 drafts per run, not scored automatically.
